# make-mate

## Problem Statement

`make` is ubiquitous, stable, and well understood by both humans and coding agents, but it is awkward as a day-to-day task runner. Its tab completion is limited, task discovery is poor, and passing structured arguments to PHONY targets is less ergonomic than tools such as `just`.

`make-mate` makes Makefile-based task runners easier to use without giving up the portability, familiarity, and fallback behavior of plain `make`.

## Target Audience

`make-mate` is for developers and teams who want `just`-style ergonomics while keeping standard Makefiles as the source of truth.

Primary users include:

- Humans invoking generated or hand-written project commands.
- Coding agents generating project automation.
- Teams that insist on plain `make` but want optional convenience features on top.
- Teams in constrained corporate environments where installing niche tooling is difficult.
- Open-source maintainers who want contributors to be able to fall back to plain `make`.

## Goals

- Provide an “easier make” experience for Makefiles that are mostly composed of PHONY task targets.
- Keep Makefiles fully useful under plain `make`.
- Give humans fast, useful tab completion for common project commands.
- Define simple conventions that coding agents can generate reliably and humans can read and edit.
- Preserve predictable `make` behavior rather than inventing a new task-runner language.
- Make installation straightforward through `uv tool install`.

## Key Features

- A CLI command named `mate` that acts as a thin wrapper around `make`.
- Target discovery for task-style Makefiles.
- Tab completion for target names, target descriptions, and declared argument names or placeholders.
- A comment-based argument declaration convention near each target, supporting required arguments, optional arguments, and defaults.
- Argument passing via ordinary make variables so equivalent plain-`make` invocations remain possible.
- Clear errors for missing or unknown arguments.
- Predictable exit codes that reflect the underlying `make` result.
- Machine-readable output where useful for completion, introspection, or coding-agent workflows.
- Low-latency, token-efficient output suitable for both humans and coding agents.

## Constraints & Assumptions

- Makefiles written for `make-mate` must remain compatible with plain `make`; any `make-mate` metadata should live in comments, ordinary make variables, or optional companion configuration that plain `make` can ignore.
- The primary target is simple task-runner Makefiles, not every possible advanced or unusual Makefile pattern.
- `make-mate` should rely on `make` itself for Makefile interpretation rather than replacing make’s parser.
- Completion logic should live in the `mate` binary, with shell completion stubs kept stable and minimal.
- Argument value completion is not required initially, but the design should leave room for it later, potentially through a separate `mate` configuration file.
- The project should be implemented in Rust and distributed as a native binary through Python wheels installable with `uv`, likely using maturin.

## Non-Goals

- Inventing a new task-runner language.
- Reimplementing `make` or replacing make’s parser.
- Requiring Makefiles to stop working with plain `make`.
- Supporting arbitrary dynamic shell-side completion logic.
- Becoming a general build system.
- Handling every possible Makefile edge case or unusual make feature.
- Chasing broad `just` feature parity when the feature would undermine make compatibility or simplicity.

## Success Criteria

- A developer can replace a `justfile` with a mostly-PHONY Makefile and get comparable day-to-day ergonomics through `mate`.
- Tab completion is fast and useful enough to be used constantly.
- A coding agent can generate a compatible Makefile from a short convention document.
- Plain `make <target> VAR=value` remains a viable fallback for every `make-mate` task.
- `uv tool install make-mate` works on common macOS, Linux, and Windows environments.
- Errors are clear enough for both humans and coding agents to diagnose failed invocations quickly.

## Open Questions / Risks

- Enumerating targets through make’s database may evaluate expensive or side-effectful `$(shell ...)` expressions during parsing.
- Caching target metadata correctly may be tricky when Makefiles include other files.
- Argument metadata could grow into an accidental mini-language if not kept constrained.
- Rust-to-PyPI packaging should be straightforward but still adds release complexity.
- Shell-specific completion behavior may differ enough to complicate support.
- The fallback for unsupported Makefile patterns should be simple: users can always invoke plain `make`, which they were already relying on.
